# Single-user venv at /home/jupyterhub/state/user-venv.
#
# This lives under state/, not under a release, so it is shared by every user and
# every release and no rollback can revert it. activate-release.sh updates it
# last, only once a release is verified serving, and never during a build that
# might be discarded. To revert by hand, reinstall from a freeze in
# state/backups/pip-freeze-user-<timestamp>.txt.
#
# Nothing here is what users actually run. The notebook server and the default
# python3 kernel both come from the hub venv; this venv supplies VIRTUAL_ENV and
# the front of PATH for terminals and subprocesses, so these packages are the
# `jupyter` CLIs a shell picks up. That is why minor bounds are fine here while
# the user-facing entries in requirements-hub.txt are patch-only.
#
# Note the decoy: this venv also contains share/jupyter/kernels/python3, which is
# NOT on the server's kernel search path (that is ~<user>/.local/share, then the
# hub venv's, then /usr/local and /usr). Only a terminal's `jupyter` CLI sees it,
# which is why `jupyter kernelspec list` from a notebook shell reports a kernel
# the server never uses.
#
# Framework packages deliberately do not belong here: they would be installed
# once, shared by everyone, and impossible for any one user to version
# independently. Users build their own environments and register their own
# kernels under ~/.local/share/jupyter/kernels.
#
# ipykernel arrives transitively and is not pinned, since nothing depends on this
# copy. The pin that matters is in requirements-hub.txt.
