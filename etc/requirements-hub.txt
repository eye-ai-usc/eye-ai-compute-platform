# Hub-side packages, installed into the per-release venv at
# /home/jupyterhub/current/venv.
#
# Bounds matter because the weekly update timer runs pip with --upgrade, so an
# unbounded requirement installs a new upstream release unattended. They are not
# schema protection: JupyterHub ships alembic migrations in minor releases, and
# bootstrap-jupyterhub.sh handles those by backing up and migrating. What a bound
# guards against is what a migration cannot fix -- renamed or removed config
# traits, authenticator contract changes, spawner behavior -- none of which
# surface until somebody tries to log in.
#
# Raise a bound by editing here and redeploying with install-jupyterhub-service.sh.
# Do not edit the venv on the host. A freeze of what is actually installed lands
# in state/backups/pip-freeze-hub-<timestamp>.txt after every successful install.

# Hub-internal: minor releases install unattended. Server-side, and minor
# releases carry security fixes worth getting promptly.
jupyterhub~=6.0
oauthenticator~=17.4

# User-facing: patch-level only, so the weekly timer cannot change what users see
# without a reviewed edit here.
#
# This venv provides the notebook server and the default python3 kernel, not just
# the hub: c.Spawner.cmd points at current/venv/bin/jupyterhub-singleuser, and a
# notebook on the default kernel reports sys.prefix = current/venv. So a
# jupyterlab minor changes the interface everyone works in, and an ipykernel
# minor changes the kernel everyone without their own environment runs.
jupyterlab~=4.6.3
ipykernel~=7.3.0
